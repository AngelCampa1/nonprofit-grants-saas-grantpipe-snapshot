# PostHog Tracking Plan

Last updated: 2026-06-18

This plan defines how GrantPipe uses PostHog to answer product and marketing
questions without collecting donor, grantee, financial, auth, or raw visitor
input data. Canonical product event names live in
`packages/shared/src/constants/analytics.ts`; this document explains how those
events should be interpreted and extended.

## Funnel Model

1. Visitor engages with public content: pageview, scroll, section, search, FAQ,
   and `cta_clicked` events.
2. Visitor becomes known intent: `lead_created`, `lead_magnet_unlocked`,
   `ai_sdr_session_started`, or app `signup_started`.
3. User creates an account: `signup_submitted`, `signup_completed`, or
   `signup_failed`.
4. User reaches setup value: onboarding events plus first created contact,
   grant, and fund.
5. Organization becomes activated: `activation_completed` after the required
   first-value events have all occurred.
6. Organization monetizes: plan, upgrade, checkout, subscription, payment, and
   billing portal events.
7. Organization retains: repeated meaningful product events over rolling
   periods, report generation, imports, accounting actions, and recovered
   payments.

## Identity Model

| Surface            | Identity                                                  | Notes                                                                           |
| ------------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Public site        | Anonymous PostHog distinct ID until lead/signup           | Do not identify with email or name. Public events use stable slugs and buckets. |
| Web app client     | User distinct ID and organization group after auth        | `identify` must not send email, name, org name, or invite tokens.               |
| API server         | Organization-scoped capture through integrations provider | Server payloads must use canonical event constants when available.              |
| External reviewers | Scoped reviewer/user identity only                        | Do not include document IDs, report IDs, names, or raw access URLs.             |

## Naming Rules

- Event names use lower snake_case.
- Do not introduce dotted GrantPipe event names such as
  `billing.portal.opened`.
- Third-party event type mirrors may keep provider-native names when they are
  stored as provider event records, for example Stripe webhook names.
- Add new first-party product events to `ANALYTICS_EVENTS` when they feed
  dashboards, funnels, activation, billing, or retention reporting.
- Prefer stable IDs and enum-like dimensions over labels.

## Property Policy

Never send:

- Email addresses, names, phone numbers, invite tokens, session IDs, access
  tokens, raw URLs with query strings, filenames, document contents, report
  titles, donor names, grantee names, funder names, notes, or free-form search
  text.

Use buckets for:

- Counts, file sizes, money values, result counts, row counts, scores, durations,
  and search/query length.

Allowed examples:

- `plan_tier`, `billing_cycle`, `entity_type`, `source`, `surface`,
  `failure_type`, `field_key`, `page_path`, `destination_path`, `section`,
  `buyer_stage`, `placement`, `intent`, `mime_family`, `size_bucket`,
  `result_count_bucket`, `query_length_bucket`.

## Dashboard Automation

GrantPipe PostHog dashboards are managed as code by
`scripts/posthog-dashboards.ts`.

The dry-run command verifies that every canonical event in
`ANALYTICS_EVENTS` belongs to at least one decision dashboard:

```bash
pnpm run posthog:dashboards -- --dry-run
```

The sync command creates or updates the PostHog dashboards and insights through
the PostHog private API. It requires a personal API key with dashboard and
insight write scopes:

```bash
POSTHOG_APP_HOST=https://us.posthog.com \
POSTHOG_ENVIRONMENT_ID=12345 \
POSTHOG_PERSONAL_API_KEY=phx_... \
pnpm run posthog:dashboards -- --apply
```

The provisioned dashboards are:

- `GrantPipe - Acquisition and Signup`
- `GrantPipe - Activation and Onboarding`
- `GrantPipe - Product Adoption`
- `GrantPipe - Billing and Retention`
- `GrantPipe - Friction and Support`

Do not add a canonical event without also assigning it to a dashboard insight;
`scripts/posthog-dashboards.test.ts` enforces that coverage.

## Open Coverage Gaps

The current canonical dashboard manifest covers every canonical event in
`ANALYTICS_EVENTS`, and `scripts/analytics-event-governance.test.ts` scans
emitted `captureEvent`, `captureRedirectEvent`, and marketing `trackEvent`
literals so durable events cannot drift outside the shared registry. Low-level
CRM feedback-widget loader events are explicitly classified as technical
telemetry rather than decision-dashboard events.

API-side capture is still narrower than client capture. Core mutations that can
happen outside the SPA, or that must survive ad blockers and client-side
PostHog failures, need server-side events with privacy-safe properties. The
priority API mutation surfaces identified in this audit are now covered.

## Validation Checklist

For every analytics change:

1. Write a failing test for the event name, trigger, and safe properties.
2. Confirm the failing test fails for the intended reason.
3. Implement the smallest change that emits the event.
4. Verify targeted tests, typecheck, lint, and coverage for touched packages.
5. Search for raw text, IDs, tokens, filenames, and unbucketed counts in event
   properties.
6. For feature failure paths, verify handled failures also reach Sentry with
   safe tags and extras. Do not send names, notes, raw input, IDs, or money
   amounts to Sentry context.
7. For public site changes, verify the PostHog `before_send` URL and property
   redaction still strips query strings and token-like path segments.
8. For app/API changes, verify organization scoping remains intact and no auth
   or session values are captured.
