# Phase 1: Scaffolding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Set up the GrantPipe monorepo with all packages, tooling, dev servers, and quality infrastructure so that Phase 2+ can begin writing features immediately.

**Architecture:** pnpm workspaces + Turborepo monorepo with three apps (`web`, `api`) and three packages (`db`, `ui`, `shared`). The web app is React + Vite on Cloudflare Pages. The API is Hono on Cloudflare Workers. The database package holds Drizzle schema targeting Neon Postgres.

**Tech Stack:** React 19, Vite, TanStack Router, TanStack Query, Hono, Drizzle ORM, Tailwind CSS 4, Shadcn/UI, TypeScript, Vitest, ESLint, Prettier, Husky, lint-staged, Turborepo

**Spec:** `docs/superpowers/specs/2026-04-07-grantpipe-v1-design.md`

- [ ] **Step 8: Implement pagination validator**

Create `packages/shared/src/validators/pagination.ts`:

```ts
import { z } from "zod";
import { PAGE_SIZE_DEFAULT, PAGE_SIZE_MAX } from "../constants";

export const paginationSchema = z.object({
  page: z.string().optional().default("1").transform(Number).pipe(z.number().int().min(1)),
  pageSize: z
    .string()
    .optional()
    .default(String(PAGE_SIZE_DEFAULT))
    .transform(Number)
    .pipe(z.number().int().min(1).max(PAGE_SIZE_MAX)),
});

export type PaginationParams = z.infer<typeof paginationSchema>;
```

```ts
const PACKAGE_MAP: Record<string, string> = {
  "apps/api": "@grantpipe/api",
  "apps/web": "@grantpipe/web",
  "packages/shared": "@grantpipe/shared",
  "packages/db": "@grantpipe/db",
  "packages/ui": "@grantpipe/ui",
};

export function getAffectedPackages(stagedFiles: string[]): string[] {
  const affected = new Set<string>();

  for (const file of stagedFiles) {
    for (const [prefix, packageName] of Object.entries(PACKAGE_MAP)) {
      if (file.startsWith(prefix)) {
        affected.add(packageName);
      }
    }
  }

  return [...affected];
}
```

```ts
import { execSync } from "child_process";
import { getAffectedPackages } from "./lib/affected-packages";

function getStagedFiles(): string[] {
  const output = execSync("git diff --cached --name-only --diff-filter=ACMR", {
    encoding: "utf-8",
  });
  return output.trim().split("\n").filter(Boolean);
}

function main() {
  const stagedFiles = getStagedFiles();
  const affected = getAffectedPackages(stagedFiles);

  if (affected.length === 0) {
    console.log("No workspace packages affected by staged changes.");
    return;
  }

  console.log(`Affected packages: ${affected.join(", ")}`);

  const filters = affected.map((pkg) => `--filter=${pkg}`).join(" ");

  try {
    execSync(`pnpm turbo typecheck test:coverage ${filters}`, {
      stdio: "inherit",
    });
  } catch {
    process.exit(1);
  }
}

main();
```

## Architecture Decisions

- **Hono RPC** - type-safe client calls without codegen. `apps/api` exports `AppType`, `apps/web` imports it via `hc<AppType>()`. Full end-to-end type inference.
- **Domain-grouped API** - each domain (donors, grants, funds, compliance, etc.) has its own folder under `apps/api/src/domains/` with `routes.ts` and `service.ts`.
- **Row-level multi-tenancy** - `org_id` on every table. Middleware attaches org context from session. All queries scoped automatically.
- **Soft delete** - `deleted_at` column on all main entities. No hard deletes in application code.
- **Money as cents** - all monetary values stored and transmitted as integers (cents). Formatted on the client.
- **Grants and funds are separate entities** - many-to-many via `grant_fund_allocations`. Matches FASB ASC 958 and how Sage Intacct / Blackbaud model it.
- **Shared Zod validators** - `packages/shared/src/validators/` holds schemas used by both API (request validation) and client (form validation).
- **Activity log** - polymorphic `activity_log` table tracks all entity changes with JSONB diffs. Serves as the audit trail.
- **Custom fields** - EAV pattern: `custom_field_definitions` + `custom_field_values`. Per-org, on contacts/donations/grants.

## Task 11: Design System Context (.impeccable.md)

**Files:**

- Create: `.impeccable.md`

- [ ] **Step 1: Create .impeccable.md**

This file provides design context to AI tools when building UI. Adapted from the ideas-validation landing page context to a SaaS dashboard context.

```markdown
# Design Context

## Users

**Who:** Executive Directors, Development Directors, and Finance/Operations staff at mid-sized nonprofits ($500K-$10M budgets). They are time-poor, risk-averse, and skeptical of technology promises - many have been burned by failed Salesforce implementations. They are generally non-technical but not unsophisticated. They use the app daily at their desks and occasionally on phones between meetings.

**Context:** They arrive after signing up from the marketing site. They are setting up their org, importing donor data, and learning the system. Trust was earned on the landing page - the app must deliver on that promise immediately. Every screen should feel like it was built by someone who understands nonprofit operations.

**Job to be done:** Manage donors, track grants, maintain compliance, and generate reports without switching between systems or hiring consultants. The app replaces spreadsheets + a donor CRM + email reminders.

## Brand Personality

**Three words:** Precise, trustworthy, capable.

**Voice:** Competent without being cold. The interface communicates through clarity, not decoration. Every element exists because it helps the user accomplish a task. No feature tours, no gamification, no celebration modals for basic actions.

**Emotional goal:** Confidence and control. The user should feel that their data is organized, their deadlines are visible, and their compliance posture is strong. The interface is a source of calm in a chaotic nonprofit environment.

## Aesthetic Direction

**Visual tone:** Linear/Stripe-inspired precision applied to a data-heavy workspace. Clean typography hierarchy, generous whitespace, subtle depth through shadows. Dense when showing data (tables, ledgers), spacious when showing overviews (dashboards, summaries).

**References:** Linear (sidebar navigation, clean detail views, activity timelines), Stripe Dashboard (data density done right, clear hierarchy, professional tone), Notion (settings pages, clean forms).

**Anti-references:**

- No enterprise blandness (cluttered navs, gray-on-gray, tiny fonts)
- No consumer playfulness (gradients, illustrations, animated celebrations)
- No startup minimalism taken too far (missing affordances, unclear CTAs, too much whitespace in data-heavy views)

**Theme:** Light mode only for V1. Must be equally polished in data-dense views (tables with 50+ rows) and spacious views (dashboard cards).

## Design Principles

1. **Data density with clarity.** Nonprofit staff manage hundreds of donors and dozens of grants. Tables, ledgers, and lists must be scannable at volume. Use typography weight, color, and spacing to create hierarchy - not borders and boxes around everything.

2. **Earned trust through craft.** The quality of the interface is proof that the product is competent. Sloppy alignment, inconsistent spacing, or janky interactions will confirm every fear an ED has about switching from their known workflow. Every pixel matters.

3. **Progressive disclosure.** Show the most important information first. Detail views use tabs. Modals handle quick-create actions. The user never needs to navigate away from their current context to log a note, record a donation, or check a deadline.

4. **Quiet confidence, not noise.** Animations are subtle and functional - acknowledge user actions, guide attention during transitions. No celebration confetti, no bouncing notifications, no gratuitous motion. The interface is calm and professional.

5. **Accessible by default.** WCAG 2.1 Level AA compliance as baseline. Semantic HTML, keyboard navigation, screen reader support, visible focus states, reduced-motion respect. Nonprofit staff include people of all abilities and ages.

## Technical Design System Summary

- **Color architecture:** Primary green (#065f46) for brand and interactive elements. Accent terracotta (#e07a5f) for attention/alerts. Neutral scale for text and surfaces. Semantic colors for success/error/warning states. All colors defined as CSS custom properties in `packages/ui/src/globals.css`.
- **Typography:** Sora (headings - confident, modern geometric sans), IBM Plex Sans (body - readable at all sizes, professional), IBM Plex Mono (data labels, financial figures, code). Responsive sizing via clamp().
- **Spacing:** Consistent spacing scale. Generous section padding on dashboards, tighter spacing in data tables. Component gaps standardized.
- **Surfaces:** Clean card system with subtle shadows (never pure black). Sidebar is a distinct surface. Modal overlays with backdrop blur.
- **Interaction:** Two button tiers visible at any time (primary action + secondary). Hover states on all interactive elements. Loading states for async operations (skeleton loaders, not spinners). Toast notifications for mutation feedback.
- **Component architecture:** Shadcn/UI base components in `packages/ui/`. App-specific compound components (data tables, detail layouts, activity timelines) in `apps/web/src/components/`. All interactive components are React.
- **Sidebar:** Fixed left sidebar with icon + label nav items. Collapses to icon-only on narrow viewports. Hamburger drawer on mobile (<768px). Notification bell and user avatar in top bar.
- **Data tables:** Column sorting, search, filters, pagination. Rows have hover state. Bulk selection where applicable. Empty states with clear CTAs.
- **Detail views:** Tabbed layout. Activity timeline as a tab or sidebar section. Metadata displayed in a consistent card pattern. Action buttons in a top action bar.
```
