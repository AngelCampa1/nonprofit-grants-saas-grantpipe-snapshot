# Logic model to grant reporting guide

A logic model is useful only if it survives contact with reporting. Many nonprofits build one for a proposal, then leave it in a folder. Months later, staff write a grant report from memory.

Use the logic model as a reporting map. It should show what the program planned, what evidence should exist, and who owns each record.

## Start with the funded version

Find the logic model that was submitted or approved. If the funder changed the scope, use the funded version, not an early draft.

Save:

- Proposal logic model
- Award agreement
- Approved budget
- Report requirements
- Any approved changes

Do not assume the internal program plan and the funded plan are the same. A proposal may have narrowed the population, activities, or outcomes. Reports should match the award terms.

## Map inputs to budget support

Inputs are the resources used to run the program. They may include staff time, supplies, space, partners, equipment, volunteers, or matching funds.

For each input, add:

- Budget line
- Restricted fund or project code
- Source record
- Owner
- Review date

This step connects the logic model to finance. If staff time is an input, payroll allocation support may be needed. If partner services are an input, the binder may need agreements or invoices. If in-kind support is an input, valuation support may be needed.

GrantPipe can help connect restricted funds, grant budgets, deadlines, report tasks, and audit evidence. That makes the logic model easier to use after the proposal is done.

## Map activities to work records

Activities are what the program does. Examples include workshops, coaching, case management, outreach, training, food delivery, or grant-funded events.

For each activity, define:

- What counts as completed
- Where staff record it
- Who enters it
- How often it is reviewed
- What date range applies
- What privacy limits apply

Do not let an activity stay vague. "Provide support" is too broad for reporting. "Provide six job readiness workshops during the grant period" is easier to track.

## Map outputs to counts

Outputs are counts of work. They are often the easiest part to report, but only if definitions are clear.

Common outputs:

- Number of sessions
- Number of participants
- Number of referrals
- Number of applications
- Number of service hours
- Number of partner meetings

For each output, define the numerator, period, source record, and duplicate rule. If one person attends three workshops, decide whether the report counts people or attendances. Write it down before the report is due.

## Map outcomes to evidence

Outcomes show change. The Centers for Disease Control and Prevention has evaluation resources that explain program evaluation concepts. For grant reporting, outcome evidence needs to be practical.

For each outcome, add:

- Metric definition
- Source record
- Baseline if needed
- Follow-up timing
- Owner
- Review step
- Limitation notes

If the logic model says participants will increase knowledge, the report needs a way to measure knowledge. If it says families will retain housing, the report needs a follow-up rule.

Avoid claims that the records cannot support. Strong reporting is careful reporting.

## Add assumptions and risks

Logic models often list assumptions. Do not skip them. Assumptions can explain report results.

Examples:

- Program assumes partner referrals stay steady.
- Program assumes two staff roles are filled.
- Program assumes participants can attend in person.
- Program assumes matching funds are available.

If an assumption fails, record the effect. This helps the report explain changes without sounding defensive.

## Build the report crosswalk

Create a crosswalk with these columns:

- Logic model item
- Report question
- Source record
- Owner
- Due date
- Evidence location
- Review status

Use the crosswalk during monthly check-ins. Each report question should have a source before the report draft starts.

## Review before the next proposal

After the report is submitted, compare the logic model to reality.

Ask:

- Which activities changed?
- Which outputs were easy to count?
- Which outcomes were hard to support?
- Which assumptions failed?
- Which metrics should change next time?

This review improves the next proposal. It also prevents the team from copying a logic model that created reporting problems.

A logic model should not be a static proposal attachment. It should be a working bridge between program plans, grant compliance, finance records, deadlines, and the evidence behind the report.
