# Data quality review before a grant report

Grant reports often go wrong before anyone starts writing. The issue is not the narrative. The issue is the data behind it.

A count may use the wrong date range. A survey result may include people outside the grant. A financial number may not match the restricted fund. A case note may support a service, but not the outcome named in the report.

A data quality review finds those problems before the report is sent.

## Start with the report questions

Read the report form first. Do not start by pulling every available export. The report questions should decide which data matters.

List each required number:

- Question or measure
- Report period
- Required format
- Source system
- Owner
- Review date
- Final approval

This list becomes the review map. It also shows where the team needs program, grants, or finance review.

## Check the date range

Date range errors are common. A quarterly report may pull year to date data. A fiscal year report may miss late entries. A survey export may use completion date instead of service date.

For each source, confirm:

- Start date
- End date
- Date field used
- Time zone if relevant
- Late entries
- Records outside the period

Save the date filters with the evidence. If a system does not preserve filters, add a note to the report packet.

## Check definitions

Many report errors come from undefined terms.

Define:

- Participant
- Household
- Visit
- Completion
- Referral
- Outcome
- Active case
- Unduplicated count

If staff use different definitions, stop and agree on one rule before reporting. The rule should match the funder requirement when one exists.

Do not change definitions just to make the number look better. If a definition changes because the old one was wrong, write a correction note.

## Check duplicates and missing data

Duplicate and missing records can change the report.

Look for:

- Duplicate participant records
- Repeat visits counted as unique people
- Missing survey responses
- Blank demographic fields
- Service records without dates
- Outcome records without a matching participant
- Records assigned to the wrong program

Fix errors in the source system when possible. If the team fixes only the spreadsheet, the same error may return next quarter.

## Check privacy

Grant evidence should not expose more data than needed. Before saving source files, remove fields that do not support the report.

Ask:

- Does the grant file need names?
- Can a summary support the number?
- Are small groups easy to identify?
- Does the file include sensitive notes?
- Who can access the folder?

Use approved storage. Do not leave private exports in downloads folders or email threads.

## Compare the story to the data

Once numbers are checked, read the draft report next to the source notes.

The narrative should match the data strength. If the data shows attendance, say attendance. If the data shows survey change for only survey respondents, say that. If the source is incomplete, do not write around the gap.

This is where program review matters. Program staff can explain why a number changed. Grants staff can decide how to write it without overclaiming.

## Save the review trail

The final packet should show how the report numbers were approved.

Save:

- Report requirement map
- Source exports or summaries
- Definition notes
- Duplicate check
- Corrections
- Program approval
- Finance approval if needed
- Final report
- Submission receipt

GrantPipe can help teams keep these checks with the grant record, due date, report status, and evidence file. That makes the next report easier because the prior rules are visible.

## Close the loop after submission

After submission, keep any funder questions with the packet. If a number is corrected, save the original number, corrected number, reason, reviewer, and date.

Use the review to improve the next cycle. If data was late, add an earlier deadline. If definitions were unclear, add them to the data dictionary. If staff had to clean the same field by hand, fix the intake process.

A good data quality review is plain work. It checks source, date, definition, privacy, approval, and final wording. That is what makes a grant report easier to trust.
