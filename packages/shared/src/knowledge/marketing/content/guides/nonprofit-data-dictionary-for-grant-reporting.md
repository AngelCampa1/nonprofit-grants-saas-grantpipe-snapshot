# Nonprofit data dictionary for grant reporting

A grant report can fail even when the program did good work. The problem is often the data. Staff use the same word in different ways. One person counts enrolled clients. Another counts clients served this quarter. A third person removes duplicates by household.

A data dictionary fixes that confusion. It tells the team what each field means, where it comes from, who owns it, and how it is checked.

This guide is for grant reporting operations. It is not a privacy policy or legal rule. Use your funder terms and data policies when deciding what to collect and share.

## Start with report fields

Do not build the dictionary from every field in every system. Start with grant report fields.

List the fields that appear in funder reports. Include client counts, services, outcomes, demographics, attendance, budget fields, narrative facts, and dates.

For each field, copy the funder wording. Then add the internal name staff use. This helps when the funder says "participants" but staff say "clients" or "members."

## Define each term in plain words

Each field needs a clear definition. The definition should answer what is counted and what is not counted.

Weak definition: "Active clients."

Better definition: "People who received at least one eligible service during the report period."

Weak definition: "Completed program."

Better definition: "People who attended at least six sessions and completed the exit survey."

Clear definitions reduce cleanup later. They also make staff more confident when a funder asks how a number was built.

## Name the source record

Every reporting field should have a source. The source may be a CRM, case management system, spreadsheet, attendance log, survey, finance system, or signed form.

Write the exact source name. If the source is a spreadsheet, name the file and folder. If the source is a database, name the table or report if staff know it.

Avoid "ask program staff" as a source. A person can own the field, but the source should be a record.

## Name the owner

Each field needs one owner. The owner is the person or role responsible for keeping the definition current and answering questions.

The owner may not enter the data. For example, front desk staff may enter attendance, but the program manager may own the attendance definition.

Use roles when possible. Staff change. Roles help the dictionary survive turnover.

## Add format and allowed values

Some fields need a format. Dates should use one date rule. Yes or no fields should use allowed values. Demographic fields should match the categories the organization has approved.

Do not let the same field accept "Y," "Yes," "yes," and "1" unless the report process can clean it.

For open text fields, explain what belongs there. A narrative note is not the same as a case note. A funder quote is not the same as a client story.

## Write the calculation rule

Any number that is calculated needs a rule. This includes unduplicated clients, completion rate, retention rate, cost per client, match, and outcomes.

Write the numerator, denominator, date range, exclusions, and duplicate rule.

For example: "Completion rate equals clients who completed six sessions divided by clients who enrolled during the grant period. Exclude clients who withdrew before the first session."

If the team cannot write the rule, the metric is not ready for reporting.

## Add privacy limits

Grant reports can include sensitive data. The dictionary should say what cannot be shared or what needs review before sharing.

This is especially important for health, housing, immigration, youth, domestic violence, and other sensitive programs. The safest report is often summary data, not raw client detail.

Write the privacy note near the field. Staff should not have to search another policy when a report is due.

## Include finance fields

Program data and finance data should connect. Add grant budget fields, expense categories, restricted fund fields, match fields, and reimbursement status when those fields support reporting.

Finance fields need source and owner rules too. A budget to actual number should come from a named finance report. A restricted balance should tie to the ledger or fund report.

GrantPipe can help keep grant records, restricted funds, report dates, and evidence in one place. A data dictionary makes those records easier to use because the team agrees on what each field means.

## Review before each report cycle

Review the dictionary before major reports. Ask whether the funder changed a field, whether staff changed a source system, or whether a metric caused confusion last time.

Keep old versions. If a definition changes, record the date and reason. This matters when reports from two periods do not match.

## Keep it short enough to use

A useful data dictionary is not a giant binder. Start with fields that affect funder reports. Add more only when they help staff report better.

The best test is simple. Give the dictionary to a new staff member and ask them to pull one metric. If they can find the source, apply the rule, and explain the number, the dictionary is doing its job.
