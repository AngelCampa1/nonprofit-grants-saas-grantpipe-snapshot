# Donor restriction coding in CRM guide

Restriction coding is where donor intent becomes daily work. A gift letter may be clear, but staff still need a usable record. The CRM should tell development, grants, and finance what the donor allowed, what the money supports, and what proof is needed before release.

This guide focuses on the CRM layer. It is not a replacement for accounting policy. Finance still decides the accounting treatment. The CRM helps staff avoid losing the donor intent before the journal entry, report, or board packet is built.

Use this with the [donor restriction intake form guide](/resources/guides/nonprofit-donor-restriction-intake-form-guide) and the [restricted gift agreement checklist](/resources/guides/restricted-gift-agreement-review-checklist).

## Start with the source document

Do not code a restriction from memory. Start with the gift agreement, award letter, email, pledge form, donor note, or board-approved campaign document.

Attach or link the source document from the CRM record. If the source is an email, save the final donor statement, not a private staff summary. If the source is unclear, mark the record as needing review.

The coding should answer one question: what did the donor actually say?

## Separate purpose and time

Most restriction coding fails because purpose and time get mixed together. Keep them separate.

Purpose restrictions name what the money can support. Examples include housing services, a scholarship fund, a food pantry, or a named program.

Time restrictions name when the money can be used. Examples include next fiscal year, a campaign period, or after a pledge payment date.

A gift can have both. Code both when both apply. Do not hide a time limit in a notes field.

## Use plain restriction types

Keep the code list short. Staff should know what each value means without a legend.

Useful CRM values include:

- no donor restriction
- purpose restriction
- time restriction
- purpose and time restriction
- endowment or board review needed
- unclear, finance review needed

Avoid values like "special," "misc," and "program." They do not tell finance what to do.

## Link to the fund code

The CRM restriction code and accounting fund code do not need to be the same field. They do need to connect.

For each restricted gift or grant, record the finance fund code, grant code, project code, or class that finance uses. If finance has not assigned the code yet, use a review status, not a guess.

FASB ASU 2016-14 focuses nonprofit reporting on net assets with and without donor restrictions. That reporting frame should influence CRM design. Staff need to know whether a gift affects restricted balances before they build reports or donor updates.

## Name the release trigger

A restricted gift should say how release will happen. Common triggers include program spending, passage of time, completion of a milestone, purchase of approved equipment, or donor approval.

Write the trigger in plain language. "Release when eligible program expenses are incurred" is better than "release later."

If the trigger depends on grant spending, connect the CRM record to the grant or fund record. If it depends on a date, record the date. If it depends on a milestone, name the evidence staff must keep.

## Require finance review

Development may enter the donor record. Finance should review restriction coding before the gift is treated as final.

Use a simple status:

- draft
- needs source
- finance review
- approved
- corrected
- closed

This status gives staff a clean way to pause work without losing the record. It also stops a proposal, receipt, or report from using an unreviewed restriction.

## Keep donor language close

Do not rewrite donor intent into vague internal terms. Keep a short donor-language excerpt or summary near the code. Use straight quotes only if the wording is exact and short.

For example, "for after-school tutoring in 2027" is more useful than "education restricted." The first line tells staff what happened. The second creates a future meeting.

## Add receipt and report links

Restriction coding should connect to donor receipts, grant reports, and board schedules. If a receipt names a restriction, the CRM should show the same restriction. If a report releases restricted money, the support should point back to the source record.

The National Council of Nonprofits notes that audits often involve requests for support and explanations. A clean CRM record helps staff answer those requests without rebuilding the history.

## Review old restricted records

Before year-end or a migration, review old restriction codes. Look for vague labels, missing fund codes, closed programs, negative balances, and records with no source document.

Do not delete old records only because they are closed. Federal award records may have retention rules under 2 CFR 200.334. Donor history may also support Form 990 work, board oversight, and future stewardship.

## Test the code set

Pick five records:

- a simple unrestricted gift
- a purpose-restricted gift
- a time-restricted pledge
- a restricted grant
- an unclear donor note

Ask development, finance, and grants staff to code each record using the same fields. If they code the same gift three different ways, the design needs work.
