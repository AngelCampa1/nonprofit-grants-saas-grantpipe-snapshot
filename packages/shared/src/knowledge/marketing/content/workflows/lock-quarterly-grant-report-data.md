# Lock quarterly grant report data

Quarterly reports move fast. Program staff send numbers. Finance reviews spending. Grants staff write the report. Then a late change arrives and no one knows which number is final.

A data lock prevents that. It freezes the approved numbers and evidence before submission. It also creates a clean change path if a correction is needed.

## Step 1: set the lock date

Pick a lock date before the report is due. The date should leave enough time for review and submission.

For a report due on the 15th, the team may lock data on the 8th or 10th. The exact timing depends on the grant, but the rule should be visible.

Put the lock date on the report calendar.

Also name who can unlock the packet. A lock date does not help if anyone can change the file without review. For small teams, the grants manager may own the lock and ask program or finance for approval when a change is needed.

## Step 2: confirm the report period

Before locking anything, confirm that program and finance use the same report period.

Check:

- Start date
- End date
- Program source dates
- Financial report dates
- Late entries
- Follow up windows

Many report errors come from one team using a quarter and another using year to date data.

## Step 3: confirm final program numbers

Review attendance, client counts, outputs, and outcomes. Each number should have a source and approval.

Save:

- Source export or summary
- Count rule
- Date filter
- Duplicate review
- Outcome calculation
- Program approval

If a number is not ready, do not lock it. Mark the issue and owner.

## Step 4: confirm final financial numbers

Finance should review any spending, match, reimbursement, or restricted fund number in the report.

Save:

- Budget to actual report
- General ledger support if needed
- Match support if required
- Restricted fund note if relevant
- Finance approval

This guide is not accounting advice. Follow the award terms, accounting policy, and reviewer guidance.

## Step 5: freeze the evidence packet

Create a locked report packet. Use a clear folder or record name with the grant, period, and lock date.

Include:

- Final draft
- Source files
- Calculation notes
- Approval notes
- Privacy review
- Change log

The packet should show what the team used for the final report.

Use a file name that makes the locked version clear. Include the grant name, quarter, and lock date. Avoid names like final, final2, or latest because they do not show which version was submitted.

## Step 6: control late changes

Sometimes data changes after the lock. A late record may be entered. A source error may be found. A funder may ask for a correction.

Allow changes, but require a trail:

- Original number
- Corrected number
- Reason
- Reviewer
- Date
- Updated report file

Do not overwrite the old file without a note.

Late changes should be rare, but they are not a failure by themselves. The problem is an untracked change. A clear change log lets the team correct real errors without losing the history behind the first approved number.

## Step 7: submit and save proof

After submission, save the final report and proof of submission. This may be a portal receipt, email confirmation, or submitted PDF.

GrantPipe can help teams connect locked numbers, evidence files, due dates, approvals, and submitted reports. That makes the next quarterly report easier to start.

If the funder asks a question later, use the locked packet first. It should show the version the team relied on when the report was sent.

If the packet is missing an approval, add the gap to the next report calendar. The lock process should improve each quarter.

## Step 8: review after submission

After the report is sent, hold a short review. Ask what caused delays or corrections.

Look for:

- Late program data
- Unclear count rules
- Financial timing issues
- Missing approval
- Privacy questions
- Report fields that need earlier review

Use the answers to improve the next quarter. A data lock is not meant to slow the team down. It gives everyone one final version to trust.
