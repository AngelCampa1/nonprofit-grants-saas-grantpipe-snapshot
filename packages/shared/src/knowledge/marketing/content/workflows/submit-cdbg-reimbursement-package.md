A CDBG reimbursement package should not be a stack of invoices with a cover sheet. It should show why each cost belongs to the approved activity and how it supports the program file.

The strongest packages are built before the due date. Finance gathers cost support. Program or grants staff confirm activity fit. A reviewer checks the request before it goes to the grantee, state, local government, or internal draw process.

Use this workflow with the broader [federal drawdown review](/workflows/review-federal-drawdown-before-request) when your CDBG process feeds a cash request.

## Step 1: confirm the activity and budget

Start with the CDBG agreement, activity setup, and approved budget. Confirm the activity name, activity number if used, budget line, period, and reimbursement rules.

Then confirm the national objective file location. The reimbursement package does not always need to repeat the whole file, but it should point to the proof that supports the activity.

Write the activity and budget line on the request. This avoids confusion when one organization has several CDBG activities open at once.

## Step 2: pull costs from the ledger

Pull ledger detail for the activity and period. The reimbursement request should start with accounting records, not a side list.

For each line, show the vendor or employee, date, amount, account, activity code, and support file. If the cost is shared, show the allocation method and the CDBG share.

If a cost is not posted yet, decide whether the rules allow it in the package. If not, hold it for the next request.

## Step 3: attach source support

Invoices should show what was bought, when, and for which work. Payroll should tie to approved time or cost allocation support. Payment records should show when the cost was paid if reimbursement requires proof of payment.

For contracts, keep the agreement, invoice, and procurement file reference. For supplies or equipment, keep receipt detail and location or use notes when needed.

Avoid sending private client data unless the agency requires it and the data handling process allows it. Use redacted or summary support when that is the right method.

## Step 4: test eligibility

Review each cost against the approved activity, HUD CDBG requirements, and any local or state instructions.

Ask these questions:

- Does the cost fit the approved activity?
- Is it inside the period?
- Is the cost supported?
- Is it reasonable for the work?
- Is it charged to the right budget line?
- Does the file show national objective support?

Remove weak costs before submission. A clean smaller request is better than a larger request that gets held up.

## Step 5: reconcile the request total

The request total should equal the support schedule. The support schedule should equal the ledger lines or explain timing differences.

Check prior requests to avoid double billing. Mark each cost as new, previously held, or corrected.

If the request includes a correction, explain it in plain words. Keep both the old and new support if a prior package changed.

## Step 6: get approval

Use a second review before submission. Finance should check the numbers. Program or grants staff should check activity and eligibility.

The approval can be a dated email, form signoff, or system note. It should include the amount approved and any costs removed.

## Step 7: save the final record

Save the reimbursement request, support schedule, ledger detail, invoices, payroll support, payment proof, eligibility notes, approval, submission confirmation, and payment record.

If the package is returned for changes, save the return note and corrected version. The file should show what changed and why.

## Before the next package

Keep a running request log by activity. Include request date, amount, costs covered, payment date, and open issues.

This log helps prevent duplicate reimbursement and supports later reporting. It also helps with [grant documentation](/resources/guides/grant-documentation-checklist-audit-ready) and closeout.

## Handle returned packages cleanly

If the agency or grantee returns the package, do not overwrite the first version. Save the return note, the original request, and the corrected request.

Then update the request log. Show which costs changed, which costs were removed, and whether the payment amount changed.

This matters because a returned package can create confusion later. Finance may see one amount in the ledger, another amount in the request file, and a third amount in the payment record.

Use a short correction memo when the change is material. It should explain the issue, the fix, and the final amount submitted.
