# Verify outcome data before submission

Outcome data should be checked before the grant report is submitted. Once the report is sent, a weak number can create follow up questions, correction work, or loss of trust.

This workflow helps teams verify the data and the words around it.

## Step 1: list every outcome in the draft

Read the draft report and mark each outcome claim.

Look for lines that say people improved, completed, retained, gained, reduced, increased, or changed. These words often need source support.

Create a table with:

- Outcome claim
- Final number
- Source
- Calculation
- Report period
- Reviewer
- Status

Do this before editing the narrative. The data should guide the wording.

## Step 2: trace each number to a source

Each outcome number should connect to a source record. The source may be a survey export, assessment result, case status, partner confirmation, or program database.

Save the source or a controlled summary. Include the export date and filters.

If the source cannot be found, do not leave the number in the report as if it is verified. Mark it for review.

## Step 3: check the calculation

Write the calculation in plain words. Include the count behind percentages.

Example:

"Thirty six of 48 participants with both pre and post surveys improved by at least one point."

This is better than "75 percent improved" with no base count. The base count helps reviewers understand the strength of the result.

## Step 4: check the report period

The outcome data should match the report period unless the funder instructions say otherwise.

Check:

- Start date
- End date
- Source date field
- Late records
- Follow up window
- Records outside the period

If the outcome uses a follow up period, explain it. For example, a job retention result may require a 90 day check.

## Step 5: review missing data

Outcome data often has gaps. Some people skip surveys. Some follow up records are late. Some partner reports arrive after the deadline.

Do not hide missing data. Decide how to handle it and save the rule.

A report can say, "Of the 48 participants with completed surveys..." That is more honest than implying every participant answered.

Also check whether missing data is random or tied to one site, class, or staff member. If one site missed survey entry, the result may not reflect the full program. Save that limit in the review notes.

If the funder requires a number even with missing data, report it with the right scope. Do not fill gaps with guesses unless the instructions allow an estimate and the method is documented.

## Step 6: check the wording

Read the narrative beside the source. The words should match the proof.

If the source shows attendance, do not claim behavior change. If the source shows self reported confidence, do not write as if an independent test proved skill gain.

Simple wording is safer and clearer.

Use the same nouns in the source and the report. If the source says survey respondents, do not change the phrase to participants unless every participant responded. If the source says households, do not call the count people.

This small wording check prevents many overstated outcomes.

## Step 7: get approval

Program staff should approve the meaning. Grants staff should approve the funder fit. An executive reviewer may need to approve high risk reports or public claims.

Save the approval with the outcome table.

GrantPipe can help teams keep outcome sources, report deadlines, review notes, and final wording together. That makes later funder questions easier to answer.

If approval changes the wording, save the approved sentence. The final report should match that sentence or show why it changed.

If the team cannot verify a result in time, mark it as blocked. Name the missing source, owner, and next action. That is better than sending an unsupported claim.

## Step 8: save the final packet

Save:

- Source records
- Calculation notes
- Missing data notes
- Privacy review
- Approval
- Final report
- Submission proof

Outcome verification is not about making the report sound smaller. It is about making the report true. A clear, supported result is better than a broad claim the file cannot prove.
